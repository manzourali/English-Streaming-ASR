# قرارداد داده و متن پایلوت مرحلهٔ ۲

نسخهٔ `persian-surt-pilot/1`، تاریخ ۲۰۲۶-۱۱-۲۰. وضعیت: پیاده‌سازی محلی آماده؛
اجرای Kaggle، دسترسی subset و پذیرش داده انجام نشده‌اند. gate مرحلهٔ ۲ **باز** است.
این مرحله هیچ mixture، feature، alignment، FastMSS، مدل یا آموزش تولید نمی‌کند.

## منبع، دسترسی و مانع فعلی

[صفحهٔ رسمی CV27 فارسی](https://mozilladatacollective.com/datasets/cmu5xazgy00finq074vaqo1b3)
در ۲۰۲۶-۱۱-۲۰ بررسی شد: شناسهٔ `cmu5xazgy00finq074vaqo1b3`، release
`cv-corpus-27.0-2026-09-11`، تاریخ انتشار ۲۰۲۶-۰۹-۱۷، قالب MP3 و مجوز CC0-1.0.
فایل منتشرشده `common-voice-scripted-speech-27-0-persia-9d86e98b.tar.gz` حدود
۱۰٫۴۶GB است. ساعت validated معادل ساعت train نیست. آمار و جزئیات corpus در همان
صفحه مرجع‌اند؛ دادهٔ پایلوت باید آمار مستقل اندازه‌گیری‌شده داشته باشد.

همان صفحه بازنشر/میزبانی مجدد داده و تلاش برای شناسایی افراد را ممنوع می‌کند.
[راهنمای رسمی API](https://mozilladatacollective.com/api-reference/docs) دریافت را
با API key و URL موقت، پس از تکمیل شرایط دسترسی در وب، مستند کرده است. endpoint
`sample-download` تنها در صورت وجود sample منتشرشده کار می‌کند؛ وجود sample مناسب
برای فارسی، metadata آن، سقف حجم و امکان انتخاب کلیپ مستقل **احراز نشده** است.
Range قابل resume برای tar.gz اثبات دسترسی تصادفی به چند کلیپ نیست.
کاربر خروجی واقعی Kaggle را ارائه کرده است: صدور لینک `/download` با HTTP 200،
دریافت Range یک‌بایتی با HTTP 206 و خواندن ۵۰۰۰ ردیف `train.tsv`. این شواهدِ ارائه‌شده
پذیرفته و ثبت شده‌اند؛ اجرای مجدد با ابزار مخزن انجام نشده است. دسترسی حساب و metadata
ابتدایی دیگر صرفاً فرض نیستند، اما دریافت subset صوتی مستقل هنوز اثبات نشده است. هیچ API key
یا signed URL ثبت نشود. کلید ارسال‌شده در چت را با کلید تازه جایگزین و فقط در Kaggle Secrets
با نام `Persian_ASR_SURT` نگه دارید؛ هیچ مقدار کلید در فایل‌های پروژه کپی نشده است.

نام Secret برابر `Persian_ASR_SURT` و نام متغیر محیطی فرایند probe برابر `MDC_API_KEY`
است؛ این دو در config جدا ثبت شده‌اند.

`access.py` روی Kaggle مستقیماً `POST /download` را با requests میزبان notebook،
بدون body و بدون Content-Type اجباری، مطابق کد موفق کاربر می‌فرستد. دیگر درخواست عمومی
کاتالوگ پیش از آن اجرا نمی‌شود؛ sample فقط با `--check-sample` بررسی می‌شود. بررسی نمونه
از دسترسی حساب جداست و sample=403 دسترسی تأییدشدهٔ download=200 را باطل نمی‌کند.
پروب HTTP در محیط عددی پین‌شده نصب یا اجرا نمی‌شود؛ نسخهٔ requests/Python میزبان در
گزارش ثبت می‌شود و محیط عددی برای تست، صوت و tokenizer همان محیط پین‌شده باقی است.
کاربر در اجرای نسخهٔ قبلی سلول ۲ب `download=403, sample=None` دریافت کرد. منشأ دقیق
این تفاوت با اجرای موفق معلوم نیست؛ هماهنگ‌سازی client و body فرضیهٔ اصلاح است و نیاز
به اجرای Kaggle دارد. نه نام Secret تغییر می‌کند و نه از این خطا باطل‌بودن کلید نتیجه می‌شود. سقف سه درخواست،
۲MiB پاسخ‌های کنترلی، ۱MiB برای هر پاسخ و ۷۵ ثانیه است؛ retry و دنبال‌کردن redirect
یا URL صوتی ندارد. این POSTها ممکن است سهمیهٔ صدور لینک حساب را مصرف کنند؛ از تکرار
بی‌دلیل پرهیز کنید. گزارش allowlist فقط status، حجم، نام فایل امن و checksum دارد؛
توکن، downloadToken، accessRecordId، پاسخ خام و URL موقت هرگز نوشته نمی‌شوند.
وجود sample، حتی با حجم مناسب، هنوز وجود متن و شناسهٔ گوینده و کفایت split را ثابت نمی‌کند.
`review/access-probe-*.json` شاهد اجرای واقعی است؛ گزارش اولیهٔ کاربر با آن یکی نیست.

[SDK رسمی](https://mozilla-data-collective.github.io/datacollective-python/) نیز از
`MDC_API_KEY` استفاده می‌کند. `download_dataset` دریافت archive است؛ load/خواندن lazy
صوت، به‌تنهایی تضمین دریافت شبکه‌ای فقط چند کلیپ نیست. بنابراین این مرحله SDK تازه نصب
نمی‌کند و از فراخوانی خودکار `download_dataset` یا `load_dataset` اجتناب می‌کند.

بخش [getFileUploadPartUrl](https://mozilladatacollective.com/api-reference/docs#getFileUploadPartUrl)
در ۲۰۲۶-۱۱-۲۰ بررسی شد: `GET /uploads/{fileUploadId}/parts/{partNumber}` یک URL موقت
برای **PUT بخش فایل در فرایند upload** می‌دهد. این endpoint مربوط به ارسال فایل توسط
منتشرکننده است؛ راه دریافت چند کلیپ از archive موجود نیست. نمونهٔ metadata کاتالوگ
یا قابلیت resume نیز به‌تنهایی index کلیپ/گوینده و دسترسی انتخابی به tar.gz نمی‌دهد.

مانع دقیق: مسیر رسمیِ زیر سقف برای دریافت صوت همراه `client_id`، source ID و متن
هنوز احراز نشده است. ابزار probe دسترسی دارد و downloader صوت ندارد؛ دانلود کامل و سپس استخراج چند فایل،
یا جایگزینی مخزن غیررسمی CV22، راه مجاز رفع این مانع نیست. باید مسیر subset رسمی
با مدرک کافی برای صوت منتخب و رعایت سقف فراهم شود؛ تا آن زمان probe بدون صوت، تست قرارداد و آرشیو وضعیت روی Kaggle قابل اجرا هستند.
private receipt یک اظهارنامهٔ اپراتور همراه ارجاع مدرک است و خودبه‌خود اثبات دسترسی نیست.

[شرایط مصرف‌کننده](https://mozilladatacollective.com/terms/consumers) و
[FAQ دسترسی خودکار و بازنشر](https://community.mozilladatacollective.com/faq-what-are-the-main-points-of-the-mdc-terms-of-use/)
نیز باید هنگام دریافت دوباره بررسی شوند. subset و restart صوتی فقط در فضای خصوصی
مجاز همان مصرف‌کننده حفظ شوند؛ اتصال به Kaggle یا نگهداری خارج از MDC باید با شرایط
واقعی دسترسی سازگار باشد. دادهٔ قابل بازنشر بودن از نام CC0 به‌تنهایی استنتاج نمی‌شود.

## شواهد تازهٔ کاربر و حد پذیرش آن‌ها

`configs/surt_pilot/user-access-evidence-v1.json` خلاصهٔ بدون هویت/متن از پیوست و hash
فایل شواهد است. archive برابر ۱۱٬۲۳۶٬۶۶۰٬۹۵۶ بایت است و checksum اعلام‌شدهٔ API ثبت
شده؛ این checksum از دانلود کامل محاسبه نشده و تأیید تمام archive محسوب نمی‌شود.
`HEAD=403` در کنار `GET Range=206` شاهدِ شکست دریافت نیست؛ ابزار نباید HEAD موفق را
پیش‌شرط GET قرار دهد. URL امضاشده می‌تواند برای متد GET کار کند؛ علت دقیق 403 در این
خروجی مشخص نشده و به‌عنوان مشکل دسترسی تعبیر نمی‌شود.

۵۰۰۰ ردیف `train.tsv` با ۹٬۶۹۹٬۳۲۸ بایت خواندنِ گزارش‌شده از archive به دست آمده و فقط
۴ گوینده گزارش شده است. این یک prefix ترتیبی است و نماینده‌بودن گویندگان یا دسترسی
به صوت‌های انتخاب‌شده را ثابت نمی‌کند. با سقف ۸ کلیپ برای هر گوینده، این pool پیش از
حذف exposure حداکثر ۳۲ کلیپ می‌دهد؛ توزیع seed ثابت بین سه split هنوز باید بررسی شود.
کد `tarfile` در حالت `r|gz` sequential است و index تصادفی برای MP3ها تولید نمی‌کند:
[مرجع Python 3.12](https://docs.python.org/3.12/library/tarfile.html).

اندازهٔ کامل TSV برابر ۹٬۴۰۳٬۲۱۵ بایت و بیشتر از سقف ۸MiB است؛ اندازهٔ واقعی بخش
۵۰۰۰ردیفی ذخیره/اندازه‌گیری نشده، پس از روی اندازهٔ کل فایل، تخلف اندازهٔ همین بخش را
نتیجه نمی‌گیریم. بااین‌حال برای رسیدن به آن بخش ۹٫۲۵MiB payload archive گزارش شده که
زیر سقف ۸MiB دریافت metadata نیست. تمام بایت‌های طی‌شده، حتی اعضای ردشدهٔ archive،
باید در حساب انتقال باقی بمانند؛ آن‌ها را برای دورزدن سقف metadata به صوت منتقل نکنید.
حداقل انتقال گزارش‌شدهٔ قبلی، با probe یک‌بایتی، ۹٬۶۹۹٬۳۲۹ بایت است و تاریخچهٔ کامل
همهٔ درخواست‌ها در دست نیست. این آزمایش دسترسی را نشان می‌دهد، ولی شاهد دریافت مطابق
تمام سقف‌های پایلوت نیست. سقف‌ها تغییر نکرده‌اند و downloader prefix خودکار فعال نشده است.

در کد پیوست `requests.get` برای بلوک‌ها بدون `stream=True` اجرا و `response.content`
پیش از کنترل حجم خوانده می‌شود؛ اگر Range نادیده گرفته شود یا پاسخ بزرگ باشد، کنترل
دیر انجام می‌شود. طول و انتهای Content-Range و total هم باید کامل تطبیق داده شوند.
این کد عیناً وارد ابزار نشده است. مسیر بعدی باید پیش از خواندن body، HTTP 206، طول،
Content-Range و encoding را کنترل کند و cache/ledger پایدار و سقف تجمعی داشته باشد؛
Range صرفاً یک روش انتقال است و تضمین اندازه یا دسترسی به کلیپ منتخب نیست.

سه ردیف قابل مشاهده در پیوست از نظر speaker hash و hash source ID در
`user-prefix-exposure-v1.json` ثبت و وارد حذف‌های plan شده‌اند. اطلاعات خام گوینده و
متن وارد Git نشده‌اند. از ۵۰۰۰ ردیف بررسی‌شده، شناسه‌های ۴۹۹۷ ردیف ارائه نشده‌اند؛
تاریخچهٔ exposure هنوز ناقص است و `finalize` آن را مانع صریح gate می‌داند. لازم است
فایل کامل ۵۰۰۰ردیفی یا ledger خصوصی همین بررسی حفظ و برای ممیزی بعدی فراهم شود؛
با سه ردیف نمی‌توان حذف تداخل تمام گویندگان/کلیپ‌های مواجه‌شده را اثبات کرد.

## سقف و ورودی

`configs/surt_pilot/pilot-v1.json` پیش از صوت فریز می‌شود: حداکثر ۳۶۰ کلیپ، ۶۰ گوینده،
۸ کلیپ برای هر گوینده، ۱۸۰۰ ثانیه، ۲۵۶MiB ورودی صوتی، ۲MiB هر کلیپ، مدت ۱ تا ۱۲ ثانیه،
metadata حداکثر ۸MiB/۵۰۰۰ ردیف و ۹۰۰ ثانیه برای هر فرمان pipeline است.
سقف دریافت شبکهٔ صوت صفر است؛ probe جداگانه فقط پاسخ کنترلی محدود API را می‌خواند.
این‌ها سقف مهندسی محافظه‌کارانه برای بررسی حداکثر نیم‌ساعت روی session Kaggle هستند،
نه برآورد نمونهٔ واقعاً در دسترس یا تضمین توان آموزش. میانگین کوتاه کلیپ‌های منبع
انگیزهٔ محدودیت تعداد است؛ نبود duration باعث رزرو ۱۲ ثانیه و نبود bytes باعث رزرو
۲MiB می‌شود، پس ممکن است خیلی کمتر از ۳۶۰ کلیپ انتخاب شود. سقف‌ها برای دورزدن خطا
افزایش داده نشوند. تغییر نسخه فقط پیش از مشاهدهٔ test و با ثبت دلیل مستقل مجاز است.

ورودی مرحلهٔ `plan` فایل JSONL محدود و خصوصی است؛ هر سطر:

| فیلد | قرارداد |
| --- | --- |
| `path` | basename اصلی کلیپ با پسوند؛ بدون پوشه/مسیر مطلق |
| `client_id` | مقدار اصلی ناشناس رسمی؛ مقدار جعلی/خالی ممنوع |
| `sentence` | متن خام رسمی |
| `locale` | `fa` |
| `validated` | boolean واقعی `true` مبتنی بر metadata منبع، نه حدس |
| `duration_metadata_seconds` | عدد ثانیه یا null؛ از زمان اندازه‌گیری‌شده جدا |
| `bytes` | حجم معتبر همان کلیپ یا null برای رزرو حداکثر |
| `original_sha256` | SHA256 معتبر فایل اصلی یا null؛ مقدار حدسی ممنوع |

این JSONL باید از metadata رسمی همان subset تهیه شود. ابزار تبدیل آرشیو کامل ندارد.
قالب خروجی وب/API به‌تنهایی چنین JSONLای را تضمین نمی‌کند؛ نبود آن مانع واقعی است.
receipt خصوصی مطابق template، SHA256 همین metadata، checksum منبع subset، تاریخ پذیرش
و بررسی دسترسی، مسیر رسمی و مدرک آن را ثبت می‌کند. template شامل null قابل اجرا نیست.
همهٔ اطلاعات ورود و هویت حساب بیرون receipt بمانند.

## split و مواجههٔ قبلی

هش گوینده دقیقاً همان mini است:
`SHA256(UTF8("cv-client:" + client_id.strip()))`؛ تغییر namespace باعث نشت می‌شود.
assignment برابر `SHA256(str(seed) + ":" + speaker_hash) mod 100` با آستانهٔ ۸۰/۱۰/۱۰ است.
seed برابر ۲۰۲۶۱۱۲۰؛ همهٔ کلیپ‌های هر گوینده فقط یک split دارند. ترتیب انتخاب مستقل
از ترتیب metadata و بر اساس hash seed/source است. source، hash اصلیِ معلوم و متن
normalized تکراری محافظه‌کارانه حذف می‌شوند. split پیش از هر augmentation و پیش از صوت
در `selection.jsonl` و `plan-lock.json` ذخیره می‌شود؛ هیچ augmentation در این کد وجود ندارد.

ممیزی محلی فقط گزارش‌های ذخیره‌شده را خوانده است: سه فایل inventory با SHA256 ثابت،
۶۰۰ source، ۱۸۳ speaker hash، ۹ original hash و ۹ canonical-waveform hash یکتا؛
هیچ ردیفِ دارای source در این فایل‌ها speaker مفقود ندارد.
`configs/surt_pilot/exposure-inventory-v1.json` مرجع این شمارش است. علاوه بر selected،
تمام inspectionهای metadata و attemptهای صوتی ناموفق هم exposed هستند.
runner فایل‌های ledger و selection موجود در outputs، runهای mini و پوشهٔ اضافی خصوصی
را نیز کشف می‌کند؛ آرشیو/attempt دیگری باید پیش از plan در پوشهٔ اضافی عرضه شود.
تمام speaker/source/hashهای مواجه‌شده از **همهٔ splitهای پایلوت** حذف می‌شوند.
هر plan تازه نیز تمام ردیف‌های metadata بررسی‌شده را در `private/exposure-ledger.json`
حفظ می‌کند؛ برای مهاجرت بعدی یا تصمیم تازهٔ متأثر از test، این ledger باید در ورودی‌های
خصوصی ممیزی بعدی قرار گیرد. بازتولید همان طرح ثابت با تغییر تنظیمات پس از دیدن test یکی نیست.

**هنوز تداخل mini با test تازه بررسی نشده است:** metadata CV27 نداریم. برابر نبودن
شناسهٔ دو release به‌تنهایی اثبات استقلال نیست؛ تداوم `client_id` باید شاهد داشته باشد.
هش canonical با همان channel mean/resample_poly/float32 little-endian mini ساخته
می‌شود؛ تغییر codec، برش یا تغییر جزئی نمونه‌ها ممکن است هش متفاوت بدهد. مدرک مستقل
برای duplicateهای بازکدگذاری‌شده لازم است؛ receipt فقط محل ارجاع آن است، الگوریتم
هش چنین ادعایی نمی‌کند. فقدان این دو شاهد در `result.json` gate را باز می‌گذارد.

پس از decode، برخورد raw/canonical با mini یا دادهٔ انتخاب‌شده حذف و دلیلش ثبت می‌شود؛
source تازه به‌جای آن برگزیده نمی‌شود و split عوض نمی‌شود. اگر هر split کمتر از دو کلیپ
باقی بماند فرمان شکست می‌خورد. دو کلیپ فقط شرط ساختاری است، کفایت آماری کیفیت نیست.

## متن نسخه‌دار `fa-latin-v1`

NFC؛ ي/ى به ی، ك به ک؛ حذف کشیده و اعراب عربی مشخص؛ ZWNJ داخل واژه حفظ و تکرارش
یکی می‌شود و در مرز فاصله حذف می‌شود. هیچ اصلاح واژه‌نامه‌ای یا افزودن نیم‌فاصله
حدسی نداریم. فاصله/کنترل/علائم و نشانه‌ها به جداکننده تبدیل و فاصله‌ها یکی می‌شوند.
حروف و اعداد Unicode حفظ می‌شوند؛ ارقام فارسی/عربی به ASCII تبدیل می‌شوند.
هیچ عدد، تاریخ، درصد یا اعشاری به گفتار حدسی بسط داده نمی‌شود: `۱۲/۰۳` به `12 03`
و `12.5` به `12 5` تبدیل می‌شود؛ این محدودیت metric باید ثابت بماند.
Latin با همان case حفظ می‌شود (`API` عوض نمی‌شود)؛ علائم `C++` یا ایمیل طبق همان قاعده
حذف/جدا می‌شوند؛ raw برای بازیابی حفظ است. کیفیت code-switching از این سیاست نتیجه نمی‌شود.
آزمون‌های idempotence، Latin، عدد، ZWNJ و کنترل نوشته شده‌اند و فقط روی Kaggle اجرا می‌شوند.

## artifact و tokenizer

`private/manifest-v1.jsonl` شامل provenance منبع/نسخه/URL، SHAها، source و speaker hash،
split، `text_raw`/`text_normalized`/policy، duration metadata و اندازه‌گیری‌شده و canonical،
rate/channel اصلی و نهایی، تبدیل و پذیرش شنیداری null است. شناسهٔ خام client فقط در
metadata خصوصی است. سلامت decode پذیرش شنیداری نیست. `exclusions-*.jsonl` و snapshot
ledger حفظ می‌شوند؛ طرح و manifest قفلِ hash دارند. خروجیِ ناقص بازنویسی نمی‌شود.

BPE فقط `train.txt` همان train را می‌بیند؛ sentencepiece 0.2.3 و config کامل پین‌اند.
`freeze.json` و `tokens.txt` معنای تمام IDها، SHA مدل/config/متن train و sourceهای train
را پیش از coverage held-out ثبت می‌کنند. fitted vocabulary/تنظیم بر اساس validation/test
تغییر نمی‌کند. train unknown و round-trip باید صفر باشند؛ گزارش validation/test توصیفی
است و هیچ حلقهٔ tune ندارد. coverage کاراکتر نسبت به train، unknown-token rate، شکست
round-trip و شمار واژهٔ Latin/unknown آن گزارش می‌شوند. نبود Latin یعنی شاهد پوشش واقعی نداریم.
test در آینده فقط برای ارزیابی نهایی کیفیت با تنظیمات ازپیش‌فریز‌شده مصرف شود؛ coverage
این مرحله مجوز انتخاب تنظیم بهتر نیست. برای نسخهٔ جدید، test مشاهده‌شده دیگر test پاکِ
تصمیم‌های متأثر از آن نیست؛ ledger باید این مواجهه را حفظ کند.

checkpoint mini با واژگان تازه **UNVERIFIED** است؛ shape مساوی کفایت نمی‌کند. مرحلهٔ
آموزش باید mapping قطعه/نقش/ID، normalization، blank/unknown و hash دو tokenizer را
ممیزی و reuse/remap/reset تمام `decoder.embedding`، `joiner.output_linear`،
`simple_am_proj`، `simple_lm_proj` و `ctc_output` وابسته به vocab را گزارش کند؛
optimizer پارامترهای تغییرکرده reset شود و strict reload/آزمون واقعی جدا لازم است.
این مرحله هیچ checkpoint را load یا remap نمی‌کند.

## تفسیر gate و تحویل

`review/status.json` وضعیت اولیهٔ باز است؛ `review/result.json` گزارش نهایی پس از اجراست.
`OPEN` یعنی مانع باقی است؛ `REVIEW_REQUIRED` هم پذیرش خودکار نیست. نبود دسترسی subset،
metadata، استقلال قابل اثبات، duplicate audit، سلامت صوت، گزارش BPE یا تست Kaggle مانع است.
threshold کیفیت و بودجهٔ آموزش مرحلهٔ ۴ هنوز تعیین نشده‌اند.
review کوچک با allowlist فقط summaryهای بدون متن/شناسه و نتیجهٔ تست دارد؛ logهای کامل
و raw/normalized text/vocabulary/receipt/صوت در restart خصوصی می‌مانند و در Git قرار نمی‌گیرند.
آرشیو review بستهٔ resume نیست. runbook روش حفظ کل run، ورودی رسمی و mini قدیمی را می‌گوید.
